# Email events: implementation plan

Companion to `docs/EMAIL_EVENTS_SPEC.md` and the engineering directives the owner supplied on 2026-11-08 (treated as one specification). Written after the investigation, before any code was changed.

## What the investigation verified

Official documentation (read 2026-11-08):

- Prompt API (developer.chrome.com/docs/ai/prompt-api, MDN, the Chromium IDL): global `LanguageModel`; `availability(options)` returns `unavailable`, `downloadable`, `downloading` or `available`, and must get the same options as `prompt()`. `create()` takes `expectedInputs`/`expectedOutputs` (text; languages `en`, `ja`, `es`, `de`, `fr`), `initialPrompts` (system, user, assistant), `signal`, and `monitor(m)` with a `downloadprogress` event whose `e.loaded` the docs multiply by 100 (range not stated). `temperature` and `topK` are extension-only and must be given together or not at all; `LanguageModel.params()` is extension-only and returns `defaultTopK`, `maxTopK`, `defaultTemperature`, `maxTemperature`. `prompt(input, { responseConstraint, omitResponseConstraintInput, signal })`. No JSON Schema subset is documented. `destroy()` ends a session. `contextUsage`/`contextWindow` (older `inputUsage`/`inputQuota` survive in extension contexts only, deprecated). A prompt that cannot fit throws `QuotaExceededError`; unsupported input throws `NotSupportedError`. Creating a session while the model is `downloadable` or `downloading` needs user activation. Available in top-level windows and same-origin iframes; a cross-origin iframe needs `allow="language-model"`. Not available in Web Workers per the docs (Chromium has a worker flag and may enable it for extension service workers; undocumented, not relied on).
- `externally_connectable` / messaging (developer.chrome.com): web pages call `chrome.runtime.sendMessage(extensionId, message, callback)`; only page-to-extension is possible; messages are JSON-serialized (64 MiB limit); `onMessageExternal` gives a `MessageSender` with `origin`. Chromium dropped the second-level-domain/eTLD restriction on `matches` in M107, so `https://cadenceaiplanning.netlify.app/*` is accepted.
- Gmail: `newer_than:`, `category:` (primary, social, promotions, updates, forums, reservations, purchases) and `-` negation are on Google's operator page; `in:inbox` is not in that table. The Gmail API `users.messages.list` documents `labelIds[]`, `includeSpamTrash`, `maxResults` (max 500) and `q`. So inbox filtering uses `labelIds=INBOX`, plus the existing after-fetch label checks.
- Google restricted scope verification: the security assessment applies "if you store or transmit restricted scope data on servers"; no local-only exemption is stated on that page.
- Not verified: whether Google's 7-day Testing-mode expiry applies to the token (implicit) flow Cadence uses (Google's page speaks of refresh tokens); Web Locks behaviour in a chrome-extension iframe embedded in a third-party page (storage partitioning may split locks). The design does not depend on either (see multi-tab below).

The code (read 2026-11-08):

- `persist()` re-reads storage before applying a change (safe across tabs). `restore()` writes a whole earlier snapshot: it must keep `sources.mail` from storage, or an Undo of an assistant change brings back deleted email events and loses newer ones.
- `converse()` (src/lib/agentllm.js) attaches `planView()` to every message: `allBusy()` events with titles, the planned work blocks and per-day minutes, all shaped by email events. Tool handlers (`check_free`, `what_if`, `remove_item`, `stayUpOption`, every change's outcome) read the same state. `views/agent.js` applies the result with `restore(result.next)`.
- Every other outbound path was checked: outline requests and own-key AI calls (`ai.js`) send assignment fields only (`reviewPlan()`, which would send a plan summary, has no callers); crew sync sends check-ins, kudos, nudges and club data; account sync sends `portable()`, which drops `sources`, `plan` and `ranked`; `recomputeState()` writes only estimates into synced tasks; the server function neither logs nor stores. The service worker makes no AI calls.
- `parse.js parseDate` reads "Friday" said on a Friday as next week and `parseClock` needs "at"; both conflict with the spec's rules, so email dates and times get their own small resolver.
- No time zone setting exists: school hours and fixed activities are local wall-clock times everywhere.
- Calendar items: `dayAgenda()` omits the event id; busy items render as plain divs in `parts.js` (timeline), `week.js` (grid) and spans in `calendar.js` (all-day markers). `calendar.js`, `account.js`, `core.refreshSources` and the service worker's autosync count every enabled entry in `state.sources` as a calendar.
- No Node; tests run in the browser from the dev server (port 8765; `netlify.toml`'s CSP forbids inline scripts).

## Decisions taken where the spec left room (each reported to the owner)

1. Time zone gap: Cadence has no school time zone. Email events are floating wall-clock times, like school hours: the date and times from the email are stored, and start/end are re-derived in the device's local time wherever events are read (`sourceEvents`). An event never moves to another day when the student travels, and daylight-saving days work through local date arithmetic.
2. Processing state (inside `sources.mail` only): `processed[messageId] = { at, status: 'done'|'retry'|'failed', engine, tries, partial }`. A Nano failure falls back to rules for that message and leaves it `retry` (re-read with Nano on a later run, at most 3 tries, replacing its rules events); a read failure leaves it `failed` (retried, at most 3 tries); an interrupted run saves nothing, so every message is read again. `dismissed[eventId] = { at, key }` (the key catches the same event under a new id after a re-read). `trash[eventId] = { at, event }` keeps a deleted event for 15 minutes so Undo can restore it, from the extension or the website.
3. Merging is stricter than the spec's minimum, as the directives ask: a newer email replaces an older event only with the same sender, the same normalised title, wording that signals a change (moved, rescheduled, changed, now, instead, new time, updated) and either the same date or the old date named in the new quote no more than a week away (the nearest such event when there are several). A cancellation removes only an event from the same sender with the same normalised title and date. A duplicate (same date, times, kind and normalised title, from any sender) is not added twice. Order does not matter: an older email read after a newer one (a retry, or one left for the next reading) does not bring back an event the newer one changed or cancelled. An event's identity is its email, date, start and kind, not its number, so re-reading an email never hides or revives the wrong event, and a deleted event's number is never reused. Undo never restores an event that a newer one replaced. (These refinements came from the independent review.)
4. Multi-tab: a storage lease (`scanStartedAt` in `sources.mail`, re-read from storage) is the guard, with Web Locks as an extra where available.
5. Website Undo: the bridge gets one more message, `cadence:mail-restore` (same validation as dismiss), because the website cannot be trusted to send event content back.
6. The assistant runs every conversation on a copy of the plan with `sources.mail` emptied and the plan recomputed, and the changes it made are replayed onto the real plan before saving. The student's own planner still plans around email events; the assistant cannot see them and may suggest a time that clashes.
7. Claims: existing claims that become untrue (`gmail-only-when-asked`, `gmail-not-saved`, `gmail-you-choose`, `gmail-bounded`, `gmail-asks-first`, `gmail-no-training`, `email-fields-to-ai`, `gmail-not-in-saved-chats`) get proofs that fail until the privacy page is reworded; code-only invariants for the new architecture are enforced now; `surface()` also fingerprints `externally_connectable`, so the lock fails until the reviewed privacy page is accepted. Those failures are the approval gate, not bugs.
8. Flagged, not changed: Cadence's own work blocks pushed to Google Calendar (opt-in, the student's own account) can sit at times chosen around email events.
